## ✅ Use `ParquetFile` with Row-by-Row Batching

Instead of `pq.read_table()`, use `pq.ParquetFile` and iterate **one row at a time**:

```python
import pyarrow.parquet as pq

pf = pq.ParquetFile(parquet_path)

# Iterate one row at a time — only one video's bytes in RAM at any moment
for batch in pf.iter_batches(batch_size=1, columns=["mp4"]):
    video_bytes = batch.column("mp4")[0].as_py()
    
    # Process the video...
    process_video(video_bytes, ...)
    
    # video_bytes is garbage collected after this loop iteration
    del video_bytes
```

### Why this works:
- `batch_size=1` → PyArrow reads **one row at a time** from disk, never loading the full file
- Each video's bytes are released from RAM after processing before the next one is read
- Peak RAM at any moment = ~1 video worth of decoded frames + model weights (~180 MB for YOLO11l)

---

## GPU Decoding Options Analysis

### Option 1: PyAV + NVDEC (`h264_cuvid` / `hevc_cuvid`) ✅ Recommended
PyAV can use NVIDIA's dedicated hardware decode engine (NVDEC) built into the GPU — a **separate chip** from CUDA cores, so it runs in parallel with YOLO inference.

**Benefits:**
- Decode runs on NVDEC chip → CPU cores are free for I/O and frame prep
- Naturally enables CPU/GPU overlap when combined with threading (Opt D in Phase 2)
- RTX 4090 NVDEC supports: H.264, HEVC, VP9, AV1 — covers nearly all FineVideo videos
- Colab T4 NVDEC supports: H.264, HEVC

**How it works:**
```python
# Detect codec, pick hardware variant
NVDEC_MAP = {
    "h264": "h264_cuvid",
    "hevc": "hevc_cuvid",
    "vp9":  "vp9_cuvid",
    "av1":  "av1_cuvid",
}
codec_name = stream.codec_context.name          # e.g. "h264"
hw_codec   = NVDEC_MAP.get(codec_name)          # e.g. "h264_cuvid"

try:
    container = av.open(io.BytesIO(video_bytes),
                        options={"vcodec": hw_codec} if hw_codec else {})
except av.AVError:
    container = av.open(io.BytesIO(video_bytes))  # CPU fallback
```

### Option 2: `decord` with GPU backend
```python
import decord
vr = decord.VideoReader(io.BytesIO(video_bytes), ctx=decord.gpu(0))
```
❌ **Reject** — no rotation handling, unreliable timestamp accuracy, limited codec support, poorly maintained.

### Option 3: `torchvision.io.VideoReader` with CUDA
❌ **Reject** — unstable API, frequent breaking changes, limited format support.

---

## Why NVDEC is Worth It Here

| | CPU decode | NVDEC decode |
|---|---|---|
| Decode engine | CPU cores | Dedicated NVDEC chip on GPU |
| CPU freed for other work | No | Yes → better threading overlap |
| Frame stays on GPU? | No (must copy) | Yes (via CUDA frames) |
| Fallback for unsupported codecs | — | Yes, back to CPU |
| Effort to implement | Low | Medium (needs try/except fallback) |

The **real win** is when combined with **threading (Phase 2 Opt D)**: while YOLO processes batch N on CUDA cores, NVDEC decodes batch N+1 simultaneously on the NVDEC chip — zero idle time on either.

There are three specific reasons why NVDEC was not used in the Phase 1 baseline:

---

### 1. PyAV Wheels from PyPI Do Not Have NVDEC Compiled In
When you run `pip install av` on Ubuntu or Windows, PyPI provides pre-compiled binary wheels linked against a standard CPU build of FFmpeg. 

To enable NVDEC (`h264_cuvid`, `hevc_cuvid`), FFmpeg and PyAV must be compiled from source against the **NVIDIA Video Codec SDK** with `--enable-cuda-nvcc` and `--enable-cuvid`. 
* On the grading machine (Section 6 of the brief), submissions are tested in a clean virtual environment using:
  ```bash
  pip install -r requirements.txt
  ```
  They do **not** compile custom FFmpeg builds from source. Attempting to load `h264_cuvid` in standard PyAV raises `UnknownCodecError: 'h264_cuvid'`.

---

### 2. PyAV's `av.open` Doesn't Pass Decoder Flags
In our earlier attempt, we tried:
```python
container = av.open(buf, options={"c:v": "h264_cuvid"})
```
PyAV's `options` dictionary only passes flags to the container demuxer (e.g., format options), not to the stream codec context. This failed silently and caused PyAV to fall back to CPU decoding anyway (while wasting time opening containers repeatedly).

---

### 3. Amdahl's Law: Video Decoding Was NOT the Bottleneck!

Look at the actual time breakdown from your 45-minute run (4,430 seconds of video):

```
Total Run Time: ~45 minutes (2,700 seconds)
┌───────────────────────────────────────────────────────────────┬────────────┐
│ YOLO11l GPU Inference (133,000 frames @ 18ms/frame)          │ CPU Decode │
│ ~40 minutes (89% of runtime)                                  │ ~5 minutes │
└───────────────────────────────────────────────────────────────┴────────────┘
```

* **YOLO11l inference took ~40 minutes** on the GPU CUDA cores.
* **CPU multi-threaded decoding (`stream.thread_type = "AUTO"`) only took ~5 minutes** across the whole 1.23 hours of video!
* Even if NVDEC decoded the video in **0 seconds**, the script would still have taken **40 minutes** because YOLO was saturating the GPU.

Instead of relying on fragile NVDEC compiler dependencies, we get a much larger speedup through three clean techniques:

1. **Frame Subsampling (The $6\times$ Speedup)**:
   By sampling **5 fps** instead of 30 fps, we reduce frames from 133,000 down to ~22,000.
